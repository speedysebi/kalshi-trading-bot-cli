# Make Kalshi trading measurable before automating it

**The CLI becomes a viable trading bot only after it demonstrates positive, executable, out-of-sample net returns and can place, reconcile, and halt orders safely under real exchange conditions.** The repository already has useful scan, backtest, paper, V2 order, and risk paths, but those are mechanisms, not proof of a profitable strategy or a reliable live system. The immediate research foundation is Kalshi's own market, trade, candle, rules, and settlement history plus a prospective order-book recorder; an external source must provide a genuine pre-decision probability estimate, because market prices alone cannot independently validate an edge. Replace Octagon in stages with a point-in-time data plane, narrowly scoped source adapters, a transparent probability model, and an execution-aware replay. Keep SQLite for operational state and evaluate Parquet with DuckDB for bulk research. Data availability and use rights are separate gates: Kalshi API storage restrictions and several external-source licenses require review for this bot's specific use. No supplied evidence establishes complete historical coverage, fillable historical prices, approved data rights, or profitable live trading.

## Current code supports research, but cannot establish executable edge

The checked-out backtest selects Octagon snapshots on or before a target date, rejects stale snapshots, and drops signals lacking per-contract volume; its metrics include Brier comparisons and event-cluster uncertainty. Yet resolved P&L enters at Octagon's `market_probability`, while fees default to `none` and the taker option uses a simplified formula. Paper positions likewise record a requested entry price without an exchange fill. These are useful forecasting and signal studies, **not realized or reliably executable return estimates** ([backtest command](../src/commands/backtest.ts), [history fetcher](../src/backtest/fetcher.ts), [metrics](../src/backtest/metrics.ts), [paper ledger](../src/commands/paper.ts)). Kalshi publishes distinct historical cutoffs for market, candle, trade, order, fill, and position data; historical candles aggregate bid, ask, and trades over an interval, but do not preserve queue position or full historical depth ([historical-data guide](https://docs.kalshi.com/getting_started/historical_data.md), [historical candles](https://docs.kalshi.com/api-reference/historical/get-historical-market-candlesticks), [order-book updates](https://docs.kalshi.com/websockets/orderbook-updates)).

The first evidence gate is a frozen, reproducible decision corpus: every candidate market, including missing and losing cases; the contemporaneous contract rules; the model and input versions; source publication and bot-observation times; quote/trade times; fee schedule; and code commit. A signal may use only information demonstrably available before its decision. Replay a sampled set from archived raw inputs, then lock chronological train, validation, and untouched test windows, grouping related event contracts to avoid leakage. Compare Brier/log loss and calibration with the contemporaneous market and simple base rates, then report **net P&L after spread, series-specific fees, slippage, partial/no fills, latency, and settlement**. Fee and fill-rate sensitivity, drawdown, capacity, and results by series, period, and liquidity should determine whether the apparent edge survives. A candle-only historical run must be labeled an assumed-fill signal backtest until prospective L2 data or a properly licensed depth archive permits execution-quality replay ([Kalshi fees](https://kalshi.com/fee-schedule), [order queue position](https://docs.kalshi.com/api-reference/orders/get-order-queue-position.md), [market rules](https://help.kalshi.com/en/articles/13823822-market-rules)).

## Safe execution requires an exchange-authoritative state machine

The V2 order builder accepts an optional `client_order_id`; its common API client retries request failures, including POST. An ambiguous response therefore requires exchange lookup before any resubmission. The current mandate checks per-order caps and local daily realized loss, but a database error makes the loss function return zero; the risk gate permits a first trade without a drawdown snapshot. These are concrete fail-open paths to close before live automation ([V2 orders](../src/tools/kalshi/orders-v2.ts), [API client](../src/tools/kalshi/api.ts), [mandate](../src/risk/mandate.ts), [risk gate](../src/risk/gate.ts)). Kalshi exposes orders, fills, positions, balance, settlements, and authenticated fill events that can anchor a durable ledger ([orders](https://docs.kalshi.com/api-reference/orders/get-orders.md), [fills](https://docs.kalshi.com/api-reference/portfolio/get-fills.md), [user fills](https://docs.kalshi.com/websockets/user-fills.md)).

Persist a unique intent before POST and carry its client ID through exchange order ID, each fill trade ID, amend/cancel, position, fee, and settlement. On timeout or uncertain acknowledgement, reconcile against the exchange before retry; order acceptance is not a fill. Reconcile on startup and after events, crossing live/historical endpoint cutoffs and treating incomplete pagination as a halt condition. Final order checks must use fresh exchange balance, positions, resting orders, market status, risk snapshot, and model data, with aggregate and per-event worst-case exposure as well as daily loss and drawdown limits. Missing or inconsistent state should block new risk. Test restarts, partial fills, cancellation races, late settlements, 429/5xx, WebSocket gaps, and kill-switch persistence. The current settlement sync itself reports an incomplete page-cap condition, and the live settlement endpoint excludes archived records ([settlement sync](../src/tools/kalshi/settle.ts), [settlements](https://docs.kalshi.com/api-reference/portfolio/get-settlements.md), [historical-data guide](https://docs.kalshi.com/getting_started/historical_data.md)).

Deploy through four evidence gates: offline deterministic replay and fault tests; live shadow decisions with quote age and hypothetical fill rules; exchange demo with mock funds and complete reconciliation; and a tightly capped live pilot whose limits and escalation owner are agreed in advance. Demo uses separate credentials and funds, so it validates behavior rather than live profitability ([API environments](https://docs.kalshi.com/getting_started/api_environments.md)). Before any live pilot, verify alert delivery and a halt/restart drill, back up and restore SQLite plus audit records, isolate and rotate credentials, review series rules and trader eligibility, and establish data retention and use permissions. Kalshi's developer agreement limits API caching/storage to facilitating the member's own trading, restricts sharing, and calls for responsible retry and monitoring; the separate Kalshi Data Terms restrict certain software, AI/ML, and archived-data uses without written consent. Their application to the intended private or distributed implementation needs a recorded review, not an assumption ([developer agreement](https://kalshi-public-docs.s3.amazonaws.com/Kalshi-Developer-Agreement.pdf), [data terms](https://kalshi-public-docs.s3.amazonaws.com/kalshi-data-terms-of-service.pdf), [API rate limits](https://docs.kalshi.com/getting_started/rate_limits.md)).

## Replace Octagon with recorded exchange data and independent evidence

Kalshi's official API should be the **primary exchange source** for event/series/market discovery, rules and lifecycle, trades, candles, current books, and settlement. Its moving historical cutoffs require querying both live and historical families and checkpointing every cursor; the documented historical inventory does not include a full-depth book archive. Start a prospective WebSocket book/trade/lifecycle recorder with periodic REST snapshots, raw envelopes, source timestamps, ingest timestamps, sequence or gap markers, checksums, and immutable rule versions. Do not infer past queue depth from present books or candles ([API index](https://docs.kalshi.com/llms.txt), [historical-data guide](https://docs.kalshi.com/getting_started/historical_data.md), [order book](https://docs.kalshi.com/api-reference/market/get-market-orderbook.md), [WebSocket guide](https://docs.kalshi.com/getting_started/quick_start_websockets.md)). Third-party Kalshi archives can accelerate validation: the [TrevorJS trade dataset](https://huggingface.co/datasets/TrevorJS/kalshi-trades) and [Kalshi Eye archive](https://kalshieye.com/data/kalshi/) are leads, **not verified coverage or licensed substitutes**; audit timestamp semantics, missing markets, correction policy, hashes, continuity, and redistribution rights before relying on either ([Kalshi Eye license](https://kalshieye.com/legal/license/)).

The replacement needs an independent estimate of outcome probability. For a first pilot, choose one contract family with explicit settlement rules and a tractable authoritative source. Macro contracts can use BLS or BEA archived releases and publication calendars; ALFRED vintages are valuable for revisions, but date-only vintage fields cannot show whether a figure was known before a release time. FRED/ALFRED API and service terms raise substantial gambling and AI-use questions, so obtain permission or use directly archived agency releases ([BLS release schedule](https://www.bls.gov/schedule/news_release/), [BEA archive policy](https://www.bea.gov/about/policies-and-information/priorities-and-schedules-posting-content), [ALFRED real-time periods](https://fred.stlouisfed.org/docs/api/fred/realtime_period.html), [FRED API terms](https://fred.stlouisfed.org/docs/api/terms_of_use.html)). Weather contracts can pair NOAA observations for labels with archived HRRR forecast runs available before the decision, but the rules' specific station, day boundary, units, and final-vs-preliminary source control the label ([GHCN-Daily](https://www.ncei.noaa.gov/products/land-based-station/global-historical-climatology-network-daily), [HRRR](https://rapidrefresh.noaa.gov/hrrr/), [Kalshi weather rules](https://help.kalshi.com/en/articles/13823837-weather-markets)).

Election certifications from state authorities, the House Clerk, or FEC support outcome labels, whereas dated state snapshots and licensed polls would be needed for live signals; a national, timestamp-complete election-night feed has not been established ([House Clerk statistics](https://clerk.house.gov/Members/ViewElectionInformation), [FEC results](https://www.fec.gov/introduction-campaign-finance/election-results-and-voting-information/)). NFLverse is useful for an offline sports baseline but upstream and separately licensed data need review; NBA.com terms bar statistics use with gambling, and Sportradar requires a contract for the specific league, latency, history, and permitted use ([nflverse](https://github.com/nflverse/nflverse-data), [NBA terms](https://api-hub.nba.com/termsofuse), [Sportradar terms](https://developer.sportradar.com/sportradar-updates/page/terms-and-conditions)). GDELT event metadata and Media Cloud story links can add dated context; source bias, first-observed timestamps, publisher-text rights, and leakage need checks. ForecastBench measures general forecasting and calibration rather than Kalshi fillability; Metaculus training/evaluation and commercial uses require permission ([GDELT data](https://gdeltproject.org/data.html), [Media Cloud FAQ](https://www.mediacloud.org/documentation/faqs), [ForecastBench datasets](https://github.com/forecastingresearch/forecastbench-datasets), [Metaculus terms](https://www.metaculus.com/terms-of-use/)).

## A small Bun replay and split storage fit this repository

Keep transactional order/risk/audit state in the existing SQLite layer and evaluate immutable Parquet files queried with DuckDB for historical joins and scorecards. SQLite WAL has same-host constraints; DuckDB can query Parquet directly, but its Bun integration and packaging still need a pilot ([SQLite WAL](https://www.sqlite.org/wal.html), [DuckDB Parquet](https://duckdb.org/docs/stable/data/parquet/overview)). Records should separate `reference_time`, `published_at`, `first_seen_at`, `decision_at`, and later `settled_at`, and preserve raw hash, rights tag, rules version, source vintage, model version, and evidence IDs. A Bun event-driven replay sharing production decision and risk logic is the shortest path to testing Kalshi-specific binary payouts, fee schedules, fills, and market lifecycle. LEAN and Zipline Reloaded are permissive cross-check candidates but require substantial custom adapters; Backtrader, Backtesting.py, and vectorbt carry different copyleft or Commons Clause constraints ([LEAN](https://github.com/QuantConnect/Lean), [Zipline Reloaded](https://github.com/stefan-jansen/zipline-reloaded/blob/main/pyproject.toml), [Backtrader](https://github.com/mementum/backtrader), [Backtesting.py](https://github.com/kernc/backtesting.py/blob/master/setup.py), [vectorbt](https://github.com/polakowo/vectorbt/blob/master/README.md)).

The code seam is clear: add Kalshi-native collectors beside `src/tools/kalshi/historical.ts` and `src/daemon/`, persist through `src/db/`, replace the Octagon-bound `src/scan/octagon-client.ts`/`src/scan/edge-computer.ts` contract with a provider-neutral evidence and probability interface, and route `src/backtest/discovery.ts`/`fetcher.ts` to the same point-in-time store. Keep `src/risk/` and `src/tools/kalshi/orders-v2.ts` as the final execution boundary and expose transparent edge components through `src/tools/registry.ts`. The first candidate should be a simple category model whose probability, uncertainty, freshness, source rights, executable price, cost, and risk rejection can each be reproduced; an opaque report is not a measurable replacement ([scan loop](../src/scan/loop.ts), [edge computer](../src/scan/edge-computer.ts), [tool registry](../src/tools/registry.ts)).

## Conclusion

The decisive dependency is a **time-correct, rights-cleared evidence chain**, not a larger model. It lets the team distinguish an actual forecasting improvement from a data leak, then distinguish a forecasting improvement from a fillable trade. Starting book capture and an exchange-authoritative intent ledger now creates evidence that historical API endpoints cannot supply retroactively; live capital should follow those measurements and recovery drills, not precede them.
